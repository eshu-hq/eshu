**A — Anchor: option (a). The marker governs; the ledger branch is retired.**

1. The alleged silent-reset hazard is **not real as stated** (“blinds dead-maintainer detection”) in as-merged code. Verified: every retrying `Fail` unconditionally rewrites `failure_details` from the cause (`failIntent` in `go/internal/storage/postgres/reducer_queue_helpers.go` → `retryReducerWorkQuery SET failure_details=$4`; `QueueFailureMetadata` in `go/internal/storage/postgres/queue/failure_metadata.go`). But the only errors that can interleave between two deferrals of the same cycle are non-wait errors (e.g. the watermark-read error in `awaitWinnersWatermark`, [handler.go](/home/ubuntu/personal-repos/eshu/go/internal/reducer/advisory/group/handler.go)), and each such Fail stores a *counting* class (`reducer_retryable` fallback). The claim freezes attempts only for non-counting classes (`reducerClaimAttemptCountCaseSQL` in `go/internal/storage/postgres/reducer_queue_readiness_sql.go`), so each marker overwrite is paid for with a counting attempt toward `MaxAttempts`. Worst case is detection delayed by one fresh 30-min window per overwriting Fail — never an infinite silent wait. Claim, heartbeat, and lease-expiry/reclaim never clear `failure_details` (verified in both claim queries); the winners wake ([reducer_waiting_winners_wake.go](/home/ubuntu/personal-repos/eshu/go/internal/storage/postgres/reducer_waiting_winners_wake.go) `wakeWinnersWatermarkQuery`) does not clear details but bumps `reopened_at`, so the handler's cycle check invalidates the old marker by design; retouch preserves details for non-terminal rows, replay NULLs them as a new cycle. Truncation cannot eat the marker (~270 B vs the 4096 B cap). The merged live proof (`TestReducerQueueClaimCarriesFailureEvidenceLive`) drives park → backstop → 3 counting stale Fails → observed `dead_letter` on real Postgres.
