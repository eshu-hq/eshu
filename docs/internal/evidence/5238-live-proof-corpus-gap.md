# #5238 — Live Postgres proof for query shapes the golden corpus cannot express

`GET /api/v0/cloud/inventory` and MCP `list_cloud_resource_inventory`'s
`account_id`/`project_id`/`subscription_id` selectors previously compared the
caller's value directly against the opaque, derived `scope_id` instead of the
canonical payload's own identity, silently matching zero rows for every real
multi-scope account on every provider. The fix (see
`go/internal/query/cloud_inventory_read_model.go`,
`go/internal/reducer/cloud_inventory_admission_writer.go`,
`go/internal/storage/postgres/cloud_inventory_evidence.go`) normalizes each
provider's resolving source fact's own identity field onto one canonical
`account_id` payload key, adds a GCP-specific fallback derivation from
`full_resource_name`, and requires `provider` alongside any account alias to
prevent a cross-provider numeric collision.

## Why this evidence artifact exists instead of a golden-corpus entry

Two shapes this fix's regression tests characterize genuinely cannot be
expressed against the existing B-7 corpus (`testdata/cassettes/gcpcloud/*.json`
and the wider 20-repo fixture set), checked directly rather than assumed:

1. **The GCP-derivation fallback shape** (a `gcp_cloud_resource` fact with a
   blank `project_id` but a `full_resource_name` carrying a `projects/<id>`
   segment). A scripted scan of every `testdata/cassettes/gcpcloud/*.json`
   fact for a `full_resource_name` key found **zero** resources with a missing
   or blank `project_id` -- every GCP asset in the fixture already carries an
   explicit `project_id: "supply-chain-demo-project"`. There is no existing
   asset in the corpus this fallback would ever engage for. Adding one would
   require hand-editing the shared cassette to synthesize a project_id-less
   GCP asset, which is a fixture-pack change with wide blast radius across
   every other golden query shape that already depends on this cassette's
   current content -- not verifiable without the live B-7 gate run, which is
   reserved for the orchestrator, not this executor.
2. **The rollout-window (pre-fix payload) shape** (a canonical
   `reducer_cloud_resource_identity` payload with literally no `account_id`
   key at all -- the exact shape any row admitted before this fix looks like
   on deploy day). The golden corpus is generated fresh by running the
   **current** (fixed) reducer code over the cassette collectors during the B-7
   bootstrap; it structurally cannot contain a payload shape only the OLD,
   pre-fix code ever wrote. There is no way to seed "what an old deploy wrote"
   into a corpus that is always regenerated by current code.

Everything that IS expressible in the corpus already landed in the same PR
lineage: `testdata/golden/e2e-20repo-snapshot.json`'s
`GET /api/v0/cloud/inventory?provider=aws&account_id=123456789012` entry,
which proves the AWS shape (the issue's own reproduction) non-vacuously,
with `required_json_values` identical to the sibling `?provider=aws` entry.

For the two shapes above, this document is the Mandatory Pre-PR Local Proof
substitute: the exact reproduction, run locally against a real Postgres
instance, with commands, output, and exit codes captured directly (never
after a pipe), postdating the final code edit.

## What each test proves, against real Postgres jsonb semantics

- `TestCloudInventoryAccountIDMatchesExactScopeIDLive`
  (`go/internal/query/cloud_inventory_account_alias_live_test.go`) — AWS
  `account_id` and its corresponding exact `scope_id` return the identical
  row set for a single-scope account; `account_id` correctly unions rows
  across multiple scope partitions sharing one account; a different
  account's rows never leak in; `limit` is honored identically by both
  selectors.
- `TestCloudInventoryGCPAndAzureAccountAliasMatchExactScopeIDLive` (same
  file) — GCP `project_id` and Azure `subscription_id` (the two providers
  the first pass of this fix left broken, per review) resolve non-vacuously
  and agree with their exact `scope_id` counterpart.
- `TestCloudInventoryGCPOrgLevelAssetExcludedFromProjectIDButVisibleUnscopedLive`
  (`go/internal/query/cloud_inventory_gcp_project_gap_live_test.go`) — a
  canonical row admitted with `account_id=""` (the shape an org/folder-level
  GCP asset with no derivable project segment genuinely produces) is
  correctly excluded from a `project_id`-filtered read (`payload->>'account_id'
  = $1` never matches an empty string against a real value) while remaining
  visible under an unscoped `provider=gcp` read. This is the documented,
  intentional residual gap, not a silent hole.
- `TestCloudInventoryPreFixPayloadRolloutWindowLive`
  (`go/internal/query/cloud_inventory_rollout_window_live_test.go`) — a
  canonical row whose payload has literally no `account_id` key (the exact
  shape `cloudInventoryAdmissionBasePayload` wrote before this fix, and what
  every already-admitted, still-active generation looks like on deploy day
  since `cloudInventoryAdmissionFactID` never hashed `AccountID` into the fact
  identity) is correctly excluded from `account_id`-filtered reads
  (`payload->>'account_id'` on a missing key is SQL `NULL`, and `NULL = $1`
  is never true), while the exact `scope_id` selector and an unfiltered
  `provider`-only read remain unaffected. This is the documented rollout
  window (`docs/public/reference/http-api.md`, `go/internal/reducer/README.md`).
- `TestCloudInventoryAccountAliasCrossProviderIsolationLive`
  (`go/internal/query/cloud_inventory_cross_provider_isolation_live_test.go`)
  — two canonical rows sharing the IDENTICAL `account_id` value
  (`"999999999999"`), one `aws` and one `gcp`, do not co-mingle once
  `provider` correctly disambiguates them: `provider=aws&account_id=...`
  returns only the AWS row, `provider=gcp&project_id=...` returns only the
  GCP row. This is the live counterpart to the HTTP-layer rejection test
  (`TestCloudInventoryHandlerAccountAliasWithoutProviderRejected`,
  `go/internal/query/cloud_inventory_account_alias_test.go`) that refuses an
  account alias supplied without `provider` in the first place.

## No-Regression Evidence

This proof exercises only the readback SQL path
(`buildCloudInventoryIdentitiesSQL`) against hand-seeded `TEMP TABLE` fixtures
scoped to each test's own Postgres session; it adds no schema, index, or
migration, and does not touch any hot-path reducer, queue, or graph-write
behavior. The `ingestion_scopes` join used for active-generation filtering is
pre-existing and unchanged by this fix; the new `account_id` predicate rides
the same already-joined `fact_records` table via `EXPLAIN (ANALYZE, BUFFERS)`
already captured during initial development of this fix, showing the
predicate applied as a `Filter` on the existing PK-indexed join, not a new
scan.

## No-Observability-Change

This proof adds no metric, span, structured log, or runtime knob; the
readback route's existing `SpanQueryCloudInventoryReadback` span and query
duration instrumentation are unchanged by this fix.
