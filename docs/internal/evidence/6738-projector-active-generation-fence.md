# #6738 projector active-generation and attempt fencing

Root-Cause Evidence: Read-only ops-qa samples on 2026-09-18 found two git scopes whose `active_generation_id` pointed to a `superseded` generation while the successor remained `pending`. The pointed source-local work had `failure_class=projector_superseded_by_newer_generation` and the same update time as the generation demotion. `ProjectorQueue.Heartbeat` demoted both work and generation before successor Ack could move the scope pointer. A disposable PostgreSQL regression reproduced the pointer gap before the fix: one active pointer, one superseded pointed generation, and one pending successor. A second RED regression showed a stale `Fail` could clear the pointer after heartbeat revoked its claim. A third RED regression showed same-owner reclaimed attempts could still Heartbeat, Ack, or Fail the newer claim because `lease_owner` is shared by replicas. A forced two-transaction PostgreSQL test also reproduced `SQLSTATE 40P01` for Ack, terminal Fail, and Heartbeat supersession: same-generation ingest held the scope and generation rows, completion held the work row, and ingest's deterministic `ON CONFLICT DO NOTHING` enqueue waited on that work row. Another real-PostgreSQL RED test used the actual ingestion commit path: a retry of published generation A with pending B and a different hint reset A to `pending`, cleared `activated_at`, and left the scope pointer naming A. A status-only patch still rewrote A's `ingested_at` after B, so Heartbeat failed to recognize B as newer. The production blank-hint claimed-source path also admits same-ID retries after publication.

The conflict domain is `scope_id`; `fact_work_items.work_item_id` and the monotonically increased `attempt_count` identify one claimed attempt. Production projector and ingester queues use one-minute and five-minute leases respectively, with heartbeat at one third of the lease; worker counts are unchanged. Claim increments `attempt_count` and returns it with the work item. Heartbeat, retry, terminal Fail, and Ack now require both owner and attempt count. Ack first updates the scope row, then checks the claimed work row before changing generations in its transaction. The scope lock serializes same-scope ingestion. Terminal Fail materializes a `FOR NO KEY UPDATE` scope lock before changing work and generation, and Ack takes the scope lock first in its transaction. Heartbeat supersession takes the scope with `FOR NO KEY UPDATE SKIP LOCKED`: ingestion holds the scope row while it streams facts, so a waiting heartbeat could outlive the one-minute lease, let another attempt reclaim the work, and reject its own next write. When the scope is busy, Heartbeat skips supersession for that tick, renews the lease, and supersedes on a later heartbeat. Any Heartbeat, Ack, or Fail rejected for a stale attempt returns `ErrProjectorClaimRejected`, which wraps `projector.ErrWorkClaimLost`; the projector service and the bootstrap-index drain drop that attempt without calling Fail and keep their other workers running, instead of stopping every worker (and, in the ingester, the collector) or aborting the bootstrap drain. A zero-row Ack work update rolls back the scope change before publication or post-commit hooks. A stale or duplicate terminal Fail changes zero rows. The retry path also rejects zero-row stale attempts. Heartbeat still supersedes older work, but retains a published active generation until successor Ack; unpublished pending generations become superseded immediately. A terminal failure of the active generation's own re-projection still fails that generation and clears its pointer, even when a successor is pending; the live Fail-before-Heartbeat case records this intended outcome. Ingestion's generation upsert keeps an existing ID's observation and ingestion chronology; only a still-pending generation can be refreshed. A same-ID retry after publication or a terminal state causes the transaction to roll back before fact writes and projector enqueue, then drains the source stream. Explicit recovery owns any re-projection of a published generation.

No-Regression Evidence: The local real-PostgreSQL RED/GREEN tests use isolated schemas. The second review also found a pre-existing Ack hazard: Ack updates the scope row first under the service's 5 s Ack budget, so a projection finishing while a same-scope ingestion commit streamed facts timed out as `ack_failed` and stopped every projector worker. A live regression holding the scope as ingestion does reproduced it (Ack failed with `context deadline exceeded` after 5.0 s). Ack now sets a transaction-local 2 s `lock_timeout` and maps SQLSTATE 55P03 to `projector.ErrWorkAckDeferred`; the test now sees the deferral after about 2.0 s with the work row, both generations, and the scope pointer unchanged, and the same Ack publishes after ingestion commits. `projector.AckWhenScopeFree` renews the lease with Heartbeat before each retry; service and bootstrap tests show a deferred Ack retried to success; the service test also shows a renewal that reports supersession ending the wait without an Ack, and a unit test shows a shutdown during that renewal ending as a deferral rather than a failed Ack. Hermetic tests show SQLSTATE 55P03 mapped to the deferral with the original error preserved, 40P01 left unmapped, and the timeout sent in PostgreSQL units (`2000ms`) and capped at 4 s so it stays inside the 5 s Ack budget. Before the fix, the published heartbeat case had one superseded old work row, one superseded active generation, one pointer still naming it, and one pending successor. Afterward, the work is superseded while the old generation remains active and pointer-consistent; successor Ack changes the old/new generation states to superseded/active and moves the pointer. If the successor calls real `ProjectorQueue.Fail`, its work becomes dead-lettered and the old active pointer remains. A duplicate old Ack or Fail after heartbeat is rejected and changes zero rows. With the same `LeaseOwner` but current `attempt_count=2`, stale attempt 1 Heartbeat, Ack, and Fail each reject and leave the running work, active generation, and pointer unchanged. The pending-old case still demotes both work and generation. A real lock-wait reclaim from attempt 2 to attempt 3 rejects stale Heartbeat, Ack, retry Fail, and terminal Fail without changing the reclaimed work, generation, or pointer. The same-generation ingest interleaving now finishes Ack and terminal Fail without deadlock; the previous build returned `SQLSTATE 40P01` for Ack, terminal Fail, and Heartbeat supersession. A later independent review found that the first lock-order fix made every Heartbeat wait on the scope row: its shipped supersession query blocked for 4,467 ms behind an open same-scope transaction with no newer generation present. The added live regression holds the scope as ingestion does, with a newer pending generation: before the `SKIP LOCKED` change Heartbeat hit its one-second deadline waiting on the scope; afterward it returned in 0.04 s with the lease renewed to about 60 s and the work and active generation unchanged, ingest completed its same-generation enqueue, and the next Heartbeat after ingest committed returned `ErrWorkSuperseded`. A PostgreSQL 18.6 lock shim confirmed the mode choice: an `ON CONFLICT DO UPDATE` upsert on the parent row made both `FOR UPDATE SKIP LOCKED` and `FOR NO KEY UPDATE SKIP LOCKED` return zero rows without waiting, while an unrelated foreign-key child insert (`KEY SHARE`) made only `FOR UPDATE SKIP LOCKED` skip the row. Projector service tests and bootstrap drain tests cover a stale attempt rejected at Heartbeat, Ack, and Fail: before the change `Run` returned the error and the bootstrap drain returned a fatal or isolated-failure error; afterward both return nil without failing the item. The actual ingestion re-commit test now leaves published A active with its original timestamp and pointer while B remains pending; a blank-hint retry of active, completed, superseded, or failed A rolls back and drains its fact stream. The liveness fixture changed from `stuck=2, aging=6` to `stuck=1, aging=7` while the recovery sweep continues to exclude a scope with another pending generation. The hosted PostgreSQL contention workflow enrolls these live regressions and the liveness/index tests; its hermetic enrollment guard failed before the filter edit and passed afterward.

Performance Evidence: On 2026-09-18, a read-only ops-qa `EXPLAIN` of the shipped liveness count had estimated cost 157,729, above that cluster's JIT threshold of 100,000. It planned a correlated sequential scan of `shared_projection_intents` for 753 active generations; catalog estimates were about 520,000 unfinished intents, and no existing index began with `generation_id`. This plan is evidence of an expensive risk, not an ops-qa elapsed-time measurement. On a disposable PostgreSQL 18 fixture with 753 active generations, 520,000 unfinished intents, 32 successor pairs, and 2,000 work rows, the original liveness query took 10.5-13.3 ms, the first materialized-CTE successor candidate took 351-392 ms with JIT and temp spill, and the final direct successor query took 10.8-12.2 ms before the new pending-generation index and 1.9-2.0 ms after it. The fixture returned identical bucket totals for all corrected candidates (`aging=232`, `stuck=521`); the original query overcounted stuck as 553 by including 32 scopes with successors. The partial index occupied 3.57 MiB and built plus analyzed in 0.249 s on this disposable fixture. This fixture favored early intent matches, so it does not prove unindexed worst-case latency. A separate sparse 753-generation/10,000-intent fixture used a one-pass hash scan and showed little index benefit (1.343 ms before, 1.204 ms after; same `aging=725`, `stuck=28`). One rolled-back 1,000-row insert in that small fixture generated 67,356 more WAL bytes with the index (297,276 to 364,632); one-sample update timing varied, so no firm write-throughput claim follows. The index adds one B-tree write for each newly unfinished intent and one removal when completed. Its live deployment cost and actual status-query latency remain to be measured after image rollout.

A separate 10,000-unrelated-generation heartbeat fixture retained the same plan and one work/one generation row updates: 0.087 ms before and 0.100 ms after in single samples. Ack now runs six statements in one transaction: a transaction-local `set_config('lock_timeout', '2000ms', true)` precedes the original five. A PostgreSQL 18.6 `pgbench` loop on loopback (2,000 transactions per variant, two runs) measured that statement at 0.011-0.013 ms of server time; in a deployment it also adds one client round trip per Ack, which was not measured. Ack runs once per projected generation. In the forced same-generation ingest contention test, Ack and terminal Fail each failed after about 1.05 s with deadlock detection before the lock-order change; after it, both completed in 0.11 s together. This is a controlled interleaving, not a fleet throughput estimate. Terminal Fail adds a materialized scope-row lock and work-row lock within its existing single statement and runs only on failure. As on main, every heartbeat runs the supersession statement and then one lease update; the supersession statement now also tries one scope-row lock without waiting. The ingestion finalized-ID skip uses the existing generation upsert statement and checks its row count without another SQL round trip; it avoids fact and work writes for already-published IDs. In a disposable PostgreSQL 18.6 shim with 200 alternating operations per variant and scenario, the original/current generation upsert p50/p95 latencies were 8.0/16.0 vs 8.0/14.1 microseconds for new inserts, 9.0/13.1 vs 10.0/14.0 microseconds for pending same-ID retries, and 10.0/15.0 vs 8.0/9.0 microseconds for active same-ID retries. The current upsert skipped all 200 active-row updates while the original demoted all 200 to pending; associated WAL sums were 71,136 vs 11,200 bytes. For 200 one-scope Heartbeat supersession operations, the original/current p50/p95 were 76.0/122.3 vs 92.0/127.1 microseconds, with 170,888 vs 169,888 WAL bytes. These small uncontended fixtures do not establish ops-qa throughput or latency. No worker-count, batch, or timeout setting changed.

Observability Evidence: A finalized-ID retry emits the existing structured ingestion commit-stage log with `stage=skip_finalized_generation` and increments the process-local skipped-refresh counter. Existing `projector work superseded by newer generation` logs include the scope and failure class. `fact_work_items` retains status, failure class, owner, attempt count, and updated time for exact-item inspection; `/admin/status` reports source-local backlog and active-generation aging/stuck counts. `eshu_dp_generation_liveness_recovered_total`, `eshu_dp_generation_liveness_failures_total`, and projector retry telemetry show recovery and retry movement. In both the projector service and the bootstrap drain, a deferred Ack logs `projector ack waiting for busy scope` at WARN on the first retry and every 30th after, with `ack_retry` and `attempt_count`. Bootstrap ends its `projector.run` span on every path that drops an item, logs a lost claim or an Ack abandoned at shutdown at WARN, and records supersession found during an Ack wait as `superseded`, as its heartbeat path already did. The Ack wait is bounded by `projector.DefaultAckWaitMaxRetries` (150 deferred Acks, about 5 minutes at the 2 s lock timeout); after that the worker logs `projector ack abandoned after waiting for busy scope` at WARN, drops the item, and lets the lease expire so a later attempt re-projects it. Service and bootstrap tests cover the bound. There is no dedicated deferral metric yet. A failed projection now records its `failed` outcome only after `Fail` confirms the attempt still owns the item, in both the service and bootstrap, and bootstrap no longer logs an expected claim loss as an ERROR `lease_heartbeat_failure`; tests assert no `failed` point or log for a lost claim. Rejected stale operations return `ErrProjectorClaimRejected`; the projector service and the bootstrap drain log `projector work claim lost to another attempt` at WARN with `operation` (heartbeat, ack, or fail) and `attempt_count`, and the heartbeat loop no longer logs that case as an ERROR `lease_heartbeat_failure`. The projector service counts neither superseded work nor a lost claim in `eshu_dp_projections_completed_total`, because the pipeline SLO divides `succeeded` by all statuses of that counter and the owning attempt records the real outcome. A heartbeat that skips supersession because the scope is busy records nothing; the durable `fact_work_items` row and the next heartbeat's outcome show progress. The existing two stale ops-qa pointers require successor Ack or deliberate recovery after this change is deployed; this code prevents the reproduced new gaps but does not silently rewrite historical rows.
