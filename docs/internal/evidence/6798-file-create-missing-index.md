# File create_missing guard on NornicDB (#6798)

Root-Cause Evidence: With the #6791 File-group probe on ops-qa (NornicDB v1.3.3), `file.*.update_existing` statements finished in at most 0.010 s and post-callback time was at most 1.46 s. `file.root.create_missing` and `file.nested.create_missing` hit the 300 s transaction timeout in 5 of 9 groups with only 1-22 rows. Both templates guarded each row with `WHERE NOT EXISTS { MATCH (:File {path: row.path}) }`. In the NornicDB v1.3.3 source (`a9956536c2cc`), `pkg/cypher/executor_mutations.go` `checkSubqueryMatch` handles an existence pattern that does not reference the outer variable by calling `loadNodesWithTemporalViewport(ctx, labels)` and filtering properties in memory. Each outer row therefore loads every File node and never consults the `File.path` index. That matches the earlier ops-qa CPU profile (`evaluateNotExistsSubquery` over `BadgerTransaction.GetNodesByLabel`) and the index's `readCount` of 0. The guard also filters nothing on this build: a live regression and a Bolt shim both showed existing files re-stamped with the new generation. Because the old guard re-stamped existing files and re-created their edges, it could also have hidden an `update_existing` write-loss; after this change `update_existing` alone owns existing files, and the offline-tier `TestFileUpdateExistingEdgesGraphTruth_ExistingFile` result below is the evidence that it keeps their edges.

Change: both templates now skip existing files with a correlated, index-backed `OPTIONAL MATCH (existing:File {path: row.path}) WITH row, existing WHERE existing IS NULL` before the Repository and Directory matches. This uses a `WITH`-attached `WHERE`, which `nornicdb-query-pitfalls.md` records as unreliable for label tests, string operators, and function calls. A bare `IS NULL` on a bound variable is none of those, and the live test proves it filters on the pinned build.

Performance Evidence: A disposable NornicDB v1.3.3 server was built from the tag with `-tags "noui nolocalllm"` and driven over Bolt with the `File.path` index online. The fixture ran the exact template text with 5 rows (3 existing paths, 2 missing) against a growing File label, with one Repository and one Directory. Each figure is a single sample.

| Files in graph | Current guard | Index-backed guard | Rows written, current / new |
| --- | ---: | ---: | --- |
| 5,000 | 0.464 s | 0.090 s | 5 / 2 |
| 20,000 | 2.025 s | 0.003 s | 5 / 2 |
| 100,000 | 5.877 s | 0.715 s first run, then 0.009-0.013 s | 5 / 2 |

The current guard grows with the File label size, not with the row count. The new guard stays flat because each row is one index seek. At 100,000 Files the first new-guard statement after bulk seeding took 0.715 s, which looks like index warm-up; three further runs on the same graph with fresh missing paths took 0.013, 0.012, and 0.009 s and each stamped only the 2 missing files. The 100,000-File index-backed samples ran on a freshly started server with a new data directory, because clearing the 100,000-node fixture with a single `DETACH DELETE` stalled. A direct `MATCH (f:File {path: $p})` took 0.3-0.5 ms throughout. The earlier 3,000-File run of the new guard also verified one `REPO_CONTAINS` and one `CONTAINS` edge per created file and no duplicate File nodes. Compose, the Helm chart, and ops-qa all pin NornicDB v1.3.3. The local build differs from the published images only in build tags, which do not touch the Cypher executor. These are fixture timings, not ops-qa latency. Deployed files-phase timing will be measured with the same probe after rollout.

No-Regression Evidence: `TestCanonicalFileCreateMissingSkipsExistingFilesLive` runs both real templates on NornicDB v1.3.3 over Bolt. Before the change, both existing files were re-stamped (`gen-1` count 0). After it, they keep `gen-1`, missing nested and root files are created once with their edges, and no duplicate nodes appear. The same test covers a batch that repeats one missing path (one node, one directory edge) and a batch where every file already exists (nothing changes). The offline-tier File-edge graph-truth tests (`TestFileUpdateExistingEdgesGraphTruth_ExistingFile`, `_BrandNewFile`) and the delta retract tests pass through the real `CanonicalNodeWriter` on the same server. `TestDeltaTombstoneGraphTruth` fails there identically on this branch and on clean `origin/main` with the same data directory, so it is not caused by this change. Hermetic writer tests now require the index-backed guard and reject `NOT EXISTS` in the create_missing statement.

No-Observability-Change: statement templates keep their IDs (`file.root.create_missing`, `file.nested.create_missing`), so the #6791 File-group probe, `eshu_dp_neo4j_query_duration_seconds`, and the canonical phase-group logs measure the new statements unchanged.
