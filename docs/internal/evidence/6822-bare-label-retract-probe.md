# Probed bare-label retract drain (#6822)

Root-Cause Evidence: On ops-qa (NornicDB v1.3.3, 1.1M nodes, image sha-55117d1), the ingester logged 36 `nornicdb retract drain completed` lines between 12:49 and 12:59Z on 2026-09-19. All 36 had `total_drained=0`, with a median of 47.5 s and a max of 54.8 s. Between 12:59 and 13:14Z it logged 108 drains totalling 5,370 s, still with 0 rows drained. Over that window projector `succeeded` stayed at 850 and `pending` rose from 435 to 489. The slow statements were all bare-label retracts: `Directory`, `AnalyticsModel`, `Annotation`, `ArgoCDApplication`, `ArgoCDApplicationSet`, `AtlantisProject`. The relationship-anchored `Repository-[:REPO_CONTAINS]->File` drain had a median of 0.01 s. The same predicate run as a read on ops-qa took 0.10-0.17 s. A local v1.3.3 shim held `SmallLabel` at 425 nodes and grew only an unrelated label. Every bare-label `DETACH DELETE` over that predicate cost 0.08 s at 20k total nodes, 0.40-0.50 s at 100k, and 7.6-9.3 s at 1M, with or without `ORDER BY`, bounded or unbounded, and even with 0 matching rows. Reads over the same `WITH ... LIMIT` stayed at 1-9 ms. Dropping `ORDER BY` from the bare-label delete form still deleted 0 rows, so it is not a fix.

Change: `BuildBoundedRetractProbeCypher` returns a bounded read for Drain-marked bare-label retracts: `... WITH n ORDER BY elementId(n) LIMIT 1 RETURN elementId(n) AS __id`. `PhaseGroupExecutor.executeDrainLoop` runs this probe once per statement. When it finds nothing, the drain is skipped. When it finds a node, the existing single-statement drain loop runs exactly as on main, until a drain step deletes zero rows. The delete stays in that one statement, so its `WHERE` clause is rechecked atomically. The probe runs once rather than per batch because it scans its own label: on ops-qa (1.1M nodes, a unique `repo_id` per run) it took 0.11 s on `AtlantisProject`, 2.9-4.4 s on `Directory`, and 31-50 s on `Function`. Relationship-anchored retracts are not probed. The retract conflict domain, `ESHU_CANONICAL_RETRACT_BATCH`, and the 5,000,000-node safety cap are unchanged. Separately, `ESHU_CANONICAL_RETRACT_BATCH`, which the ingester and projector already read, is now registered in `go/internal/envregistry`.

Rejected designs: A first version split each batch into "read element IDs, then `DETACH DELETE` exactly those IDs". Codex review found that this is unsafe. A stale attempt can select a prior-generation node, a replacement attempt can refresh that node to the current generation, and the stale delete by ID then removes a live node. A local shim reproduced this: of 30 selected nodes, 5 were refreshed, and the plain delete by ID removed all 30. Rechecking the predicate on each ID-matched node is correct: the same case deleted 25 and kept the 5 refreshed nodes. But it cost 187-292 s for 20-30 IDs on the 1M-node store, because `MATCH (n) WHERE elementId(n) = __id WITH n WHERE <predicate>` falls back to a whole-store scan. A `FOREACH`/`CASE` conditional delete deleted nothing and took 250 s. Probe-then-drain keeps main's atomic delete and removes only the no-op cost.

Performance Evidence: Setup: local NornicDB v1.3.3 built from the v1.3.3 tag, run with `--no-auth --headless` and embeddings and search disabled, over a store of 1,000,000 unrelated nodes. `TestIngesterNornicDBProbedDrainLiveKeepsCurrentGeneration` drives the real ingester NornicDB executor over the production entity-retract template with batch 50. I ran it back to back on origin/main 6e17adaaf and on this branch against the same store, two interleaved rounds. An uncached zero-match retract (a repository with no nodes, and parameters no earlier statement used) took 9.28 s and 7.93 s on main, against 0.38 ms and 0.44 ms on the branch. A backlog of 130 stale nodes plus 25 current-generation nodes took 45.3 s and 37.8 s on main, against 35.3 s and 32.6 s on the branch. The backlog path runs main's drain loop plus one probe, so I read that difference as run-to-run noise and claim no speedup, only no regression. Both versions deleted every stale node and kept every current node. On ops-qa, the savings depend on label size. A retract with nothing to delete used to cost a 45-55 s drain; it now costs the label's probe, which is 0.11 s for `AtlantisProject`, 2.9-4.4 s for `Directory`, and 31-50 s for `Function`. On a large label the probe is not free: a `Function` retract that does have stale nodes pays the 31-50 s probe on top of main's drain loop, and one with nothing to delete saves little (a 31-50 s probe instead of a 45-55 s drain). The net win on ops-qa comes from the many small and medium labels. The ops-qa effect is to be measured after deploy.

Observability Evidence: `nornicdb retract drain completed` now carries `mode` (`probe_skipped`, `probed`, `probe_failed`, or `single_statement`) and `probe_duration_s`, next to the existing `total_drained`, `batch`, and `duration_s`. `probe_failed` means the probe itself errored (fail-safe "unknown", not "zero rows") and the drain ran unconditionally rather than being skipped. An operator can therefore see which retracts ended on the probe alone, which ones fell back after a failed probe, and what each probe cost. Retracted node and relationship counts still feed `eshu_dp_reconciliation_drift_retractions_total` through `RecordReconciliationDriftRetractions`. Follow-up: the probe (`DrainReader.RunProbe`) and the drain write (`DrainReader.RunWrite`) are now separate interface methods so command-owned gate and timeout wrappers label each independently (`canonical_probe` vs `canonical_retract_drain`) instead of the probe inheriting the drain's label (#6822).

No-Regression Evidence: The follow-up comment corrections (#6822, after the #6830 merge) change comments only. `git diff 2d97d8e2b HEAD` is 5 files, +14/-11, every changed line inside a `//` comment except one `DrainReader: nil,` test field whose code is identical on both sides. No statement, signature, parameter, Cypher string or runtime knob changed, so the probe and drain call shapes, batch size, gate permits and timeouts are byte-identical to the merged code and there is nothing to re-measure; the measurements above still describe the shipped behaviour. Verified at that head: `go build ./cmd/ingester` exit 0, `go vet ./cmd/ingester ./internal/storage/nornicdb` exit 0, `go test ./cmd/ingester ./internal/storage/nornicdb -count=1` both ok, gofumpt empty, `git diff --check` exit 0.

No-Observability-Change: The comment corrections emit no signal and touch no instrumentation. `nornicdb retract drain completed` keeps the same `mode`, `probe_duration_s`, `total_drained`, `batch` and `duration_s` fields, the `probe_failed` WARN is unchanged, and the backpressure labels stay `canonical_probe` for the probe and `canonical_retract_drain` for the drain write.
