# Concurrent catalog proof accepts the one owed replay

Issue #8976. The concurrent runtime fence test rejected two materialization calls before it inspected the replay state. A successful producer ACK can flag a claimed catalog row for one replay. That row's first successful ACK returns it to pending; another catalog worker can claim and finish the replay before the first worker reports completion.

Root-Cause Evidence: readiness run [40068810308](https://github.com/eshu-hq/eshu/actions/runs/40068810308) on `bfcb20c` logged `replay_flagged_count=1` and runtime row counts `[2 2]`, then failed an assertion requiring one call. The log proves both calls had two rows, but did not retain their identities or worker order. The test source was unchanged from the passing dedicated contention run [40064150417](https://github.com/eshu-hq/eshu/actions/runs/40064150417).

The controlled regression uses the existing PostgreSQL fixture and three catalog workers on separate connections. It holds the first claim while the producer ACK flags it, checks the claimed row has the replay flag, lets the first ACK return it to pending at attempt zero, then releases two peer workers to race for the replay. One different peer claims and ACKs it. The final producer and catalog rows are succeeded at attempt one, with no replay flag or live lease. The old assertion then failed on `[2 2]` under `-race` on pinned PostgreSQL 18.6. This is a test of mock materialization calls and durable queue accounting, not a claim that two service generations were stored.

No-Regression Evidence: after the assertion was repaired, the same existing test root passed with both the unforced and controlled subtests, race detection, exact run/pass accounting, and zero skips or failures. Every materialization call must contain the prod and stage Kubernetes workload identities, and the total is one initial call plus at most one justified replay. The unforced case checks the replay marker and successful worker identities when a peer drains it; otherwise it drains the one pending replay itself. The final queue assertions require both rows succeeded at attempt one, a cleared replay flag, and no live catalog lease. The selected local event receipt is `8976-final-receipt.json` in the goal's retained proof artifacts; hosted readiness and contention acceptance remain pending.

No-Observability-Change: production code and production signals are unchanged. The existing producer ACK log includes `replay_flagged_count`; the proof adds worker and queue-state diagnostics for failures. The contested resource is the catalog `fact_work_items` row in its scope conflict domain. Three catalog workers retain separate connections and the existing one-minute lease. Before the replay, the catalog row is claimed at attempt one with its flag set; after the first ACK it is pending at attempt zero; after the peer or manual replay it is succeeded at attempt one with no lease. No timing comparison or throughput claim is made.
