## Verified facts (arbiter's own checks)

1. **OSV ground truth excludes 7.29.7.** I re-fetched `api.osv.dev/v1/vulns/GHSA-67hx-6x53-jw92` (`curl`, exit 0). Three `affected[]` entries: `@babel/traverse` SEMVER `[0, fixed 7.23.2)`; `@babel/traverse` SEMVER `[8.0.0-alpha.0, fixed 8.0.0-alpha.4)`; `babel-traverse` (unscoped, different npm package) SEMVER `introduced 0`, no fixed event. No entry covers 7.29.7 for `@babel/traverse`.
2. **The matcher cannot truthfully return `affected` here, by design at three points.** `evaluateNPMSemverMatch` returns affected only when a range or exact version contains the observed version, else known-fixed only when a scalar fixed version exists, else `possibly_affected / version_not_in_advisory_range` ([version_match.go](/home/ubuntu/personal-repos/eshu/go/internal/reducer/supplychain/core/version_match.go:163)). For a multi-line advisory the scalar fixed version is deliberately blank — #9430's rule, because one line's fix fed as "the" fix would flip other lines to known-fixed ([provenance_selection.go](/home/ubuntu/personal-repos/eshu/go/internal/reducer/supplychain/core/provenance_selection.go:269)). Findings group affected packages by `PackageID`, so the unscoped `babel-traverse` fact never enters the `@babel/traverse` finding's package set ([provenance.go](/home/ubuntu/personal-repos/eshu/go/internal/reducer/supplychain/core/provenance.go:77)).
3. **Exact-shape probe through the production matcher reproduces the live QA row and proves both directions.** I ran a throwaway test via `go test -overlay` (no repo file written; probe kept at `/tmp/arbiter9431/`) feeding the exact satellite fact shape (both ranges, `fixed_versions ["7.23.2","8.0.0-alpha.4"]`, unscoped entry co-present): `7.29.7 -> status="possibly_affected" reason="version_not_in_advisory_range" fixed="" range=">=0 <7.23.2"` — byte-identical in shape to the post-cycle QA finding; `7.23.1 -> affected_exact / npm_semver_affected_range`; `8.0.0-alpha.2 -> affected_exact`. The three committed contract tests (`TestBuildSupplyChainImpactFindingsMatchesSecondVulnerableRange`, `TestProvenanceMultiLineFactLeavesScalarFixedVersionBlank`, `TestBuildSupplyChainImpactFindingsExplainsNPMSemverRangeMatch`) also PASS (exit 0). This is the correlation-truth matrix: positive, negative, and other-line cases all behave.
4. **The original ruling's witness version was mis-specified; the issue's own text was not.** The ruling demanded `affected` for the 7.29.7-pinned deployment ([9431-arbiter-ruling.md](/home/ubuntu/personal-repos/eshu/docs/internal/evidence/9431-arbiter-ruling.md:155)). But [#9431](https://github.com/eshu-hq/eshu/issues/9431) itself names the dropped line as "`@babel/traverse` 7.0.0 to 7.23.1" and its AC asks for `affected` for "a version on a previously dropped line" (`gh issue view 9431`). 7.29.7 was never on that line; expecting `affected` for it was the error, inherited from the lane baseline comment.
5. **Retired rows cannot reappear as candidates.** The candidate predicate requires `g.generation_id = s.active_generation_id AND g.status='active'` ([9431-qa-retire.sql](/home/ubuntu/personal-repos/eshu/docs/internal/evidence/9431-qa-retire.sql:91)). A pass-1-retired row is superseded with a NULL pointer, so it is excluded by construction on any repeat pass.

## Decisions

1. **ACCEPT `possibly_affected`; AC3.3b is restated as follows and supersedes the original line.** Restated AC3.3b: *for GHSA-67hx-6x53-jw92, a version inside the previously dropped `[0, 7.23.2)` line evaluates `affected` against the live both-lines satellite facts, and the actual 7.29.7-pinned deployment — a post-fix version — reads `possibly_affected / version_not_in_advisory_range` (fail-closed), not `affected`.* Both halves are proven: half one by fact 3 on the exact live fact shape plus the committed multi-range tests, with the ranges themselves proven live on QA by AC3.3a/AC3.5; half two by the observed step-6 cycle (pending 16:50:05 → claimed 17:00:24 → succeeded 17:01:05 UTC, finding refreshed 17:01:05, now carrying `>=0 <7.23.2` — the restored line is what the live reducer evaluated against). An `affected` answer for 7.29.7 would be a false positive against OSV truth; accuracy forbids it.
2. **The DENY branch is rejected; each route to `affected` is falsified.** Only three things could make `affected` correct: an `@babel/traverse` OSV entry covering 7.29.7 (none exists, fact 1); a semver misread placing 7.29.7 below 7.23.2 (false); or aliasing unscoped `babel-traverse` onto `@babel/traverse` (wrong — OSV names two distinct npm packages, and aliasing would mark every `@babel/traverse` version affected forever). There is no version-range misread and no matcher bug to file from this evidence.
3. **`possibly_affected` rather than `known_fixed` is #9430's deliberate fail-closed design, not a defect in scope.** With no scalar fix for a multi-line advisory, the matcher cannot assert known-fixed without the cross-line compare #9430 removed. A future per-line known-fixed refinement is an optional enhancement under its own issue and prove-the-theory gate; it does not block #9431, and no filing is ordered here.
4. **`candidates=47` is ENDORSED.** Under decision 3 of the APPROVE ruling as recorded on [#9431](https://github.com/eshu-hq/eshu/issues/9431#issuecomment-6545872786) (repeat the gated pass as scopes drain), each pass recomputes the set; by fact 5 a literal 136 on pass 2 could only occur if pass-1 rows had resurrected. The accounting closes at membership level, not just by count: 89 pass-1 rows verified superseded and marked pre-commit, 47 = 46 Class S remainder + 1 drained axios Class W, committed-minus-oracle 0 and oracle-minus-committed 0 across both passes, markers and NULL pointers 90/90. Consequences: the pass-2 COMMIT stands as authorized; no rollback, no third pass (post-cycle retire set is 0, AC3.1/AC3.2 = 0).
5. **Closure clearance.** AC3.3b no longer blocks. The siblings already hold on the recorded evidence (AC3.1=0, AC3.2=0, AC3.3a both lines, AC3.4=835, AC3.5 PASS, post-cycle).
