# Admitted File Names

Repository discovery keeps a file when the parser registry binds its name or
extension. Each registry definition carries an ecosystem (the language key in
`specs/language-feature-parity-ledger.v1.yaml`, or a cross-cutting name for
Dockerfile, plain-text, and generic YAML bindings) and an admission level:

| Level | Meaning |
| --- | --- |
| L0 | Not admitted. This is the default for every name no definition binds. |
| L1 content text | Admitted to the content store as searchable text. No structured facts. |
| L2 structured fact | Admitted through a parser that emits structured entities or facts. |

L3 (graph projection) is a property of the reducer, recorded with the
projection and not in this table. Discovery also keeps documentation files and
a few special-cased names outside the registry, so the table lists registry
bindings, not every file Eshu can read.

The table below is generated from `go/internal/parser/registry_definitions.go`.
Edit the registry, then run `scripts/generate-parser-admission-doc.sh`. A drift
test in `go/internal/parser` fails when the table is stale. See
[Language Support](../contributing-language-support.md) for the contribution
checklist.

The sections outside the generated region are hand-written, and the generator
check does not cover them. `scripts/verify-required-doc-sections.sh` fails when
`## Content store policy` is missing, so a merge or squash cannot drop it. The
required headings live in `scripts/required-doc-sections.txt`, one
`<page><TAB><heading>` line each. To protect another hand-written section, add
a line there.

## Content store policy

Each registry definition also names a content-store policy, shown in the
**Content store** column above. The policy decides what the collector writes to
the content store for the files that definition binds. It is applied at the
collector write boundary, before any `content` fact or `content_files` row
exists, so search, `get_file_content`, and exports never see a body the policy
withheld. Filtering in the query layer was rejected because search and any
export would bypass it.

| Policy | What is stored | Use it for |
| --- | --- | --- |
| `store` | The body, verbatim. This is the default for every definition except `.npmrc` and `gradle-wrapper.properties`. | Source and configuration files that hold no credentials. |
| `metadata` | A `content_files` row with an empty body. The path stays in the repository tree, file counts, language inventory, and coverage. The row is never a tombstone. | Files that can hold credentials where the registry URLs or version pins matter more than the text. |
| `redact` | The body with credential values replaced in place. The `marker` mode writes `REDACTED_<finding_kind>`, for example `npmAuthToken: REDACTED_api_token`. The `skeleton` mode keeps structure, keys, and values whose shape cannot carry a credential, and writes `REDACTED_value` or `REDACTED_<finding_kind>` for every other value. | `marker`: closed-schema files where every credential key is known. `skeleton`: open-schema files such as `*.tfvars`, where a key name does not say whether the value is secret. |

A `redact` definition lists its credential keys. `marker` mode replaces the
value of each listed key at any length, keeps an exact `${NAME}` environment
reference, and also redacts a line the hardcoded-secret detector from
migration 138 matches: a key match (such as `Authorization: Bearer ...`) is
treated like a listed key and the value to the end of the line is replaced, and
a value-shape match (an AWS key, a Slack token) is replaced from the shape to the
end of the line. Every line inside a PEM `BEGIN` to `END` block is
replaced, and so are the continuation lines of a listed key's block scalar or
multi-line quoted value. The marker keeps the finding kind so
`investigate_hardcoded_secrets` can keep reporting the line. `[redacted]` and
`***` are not used: the detector cannot see them. A YAML alias anywhere in the body,
a listed key the YAML parser finds on a line the key match cannot read (an
explicit `? npmAuthToken` entry, an escaped spelling), or a listed key whose
value, in YAML flow style, continues on a line that neither the redactor
replaced nor holds only a comment, brackets, or a document marker (for
example `{`, then `npmAuthToken:` and its value on the next lines at the same
indent), could leave a secret on a line no key reads, so each stores the
metadata row instead (reason `yaml_indirection`).

A `marker` definition can also list URL-valued keys, such as `npmRegistryServer`
and `httpsProxy` in `.yarnrc.yml`. For those keys only the URL userinfo is
replaced, so `"https://user:pass@npm.example.com/"` is stored as
`"https://REDACTED_secret_literal@npm.example.com/"` and the host stays
readable. The userinfo ends at the last `@` before the first `/`, `?`, or `#`,
so a raw `@` in a password is covered. The rule fails closed: the whole value is
replaced, as for a credential key, when the value is not exactly one URL (a
trailing comment, two URLs, an environment default such as
`${REGISTRY:-https://...}`), when the host is not a plain name or IPv6 literal
with an optional numeric port (a raw `/` in a password, a percent escape), when
an `@` follows the host (a scoped path such as `/@acme/` included, because
`http://tok/en@host` may be a token holding a raw `/`), when a double-quoted
value holds a backslash (YAML decodes `\x40` to `@`), or when the line holds
any other detector match.

The `skeleton` mode is line-wise and keeps every line number. It keeps empty
lines, structural lines (`{`, `}`, `[`, `]`, `key = {`, `key = [`, and heredoc
openers and closers), and a `key = value` or `"key": value` value that is a
boolean, `null`, a number, a `var.`, `local.`, `module.`, or `data.` reference,
or a quoted version or constraint (`"14.7"`, `"~> 5.31.0"`). When the raw line
is a hardcoded-secret finding, the value becomes `REDACTED_<finding_kind>`, even
for a reference, so `db_password = var.db_password` is stored as
`db_password = REDACTED_password_literal`. Every other value becomes
`REDACTED_value`, which the detector never reports. A line it cannot place as
`key = value` (a comment, a bare list element, a heredoc body line, a PEM block
line, an unterminated string, a credential inside the key itself, or a value
that starts with `=` or `:`, such as a bare base64 `TOKEN==`) becomes the
whole-line `REDACTED_<finding_kind>` when it is a finding and `REDACTED_value`
otherwise. A heredoc or block comment opened after other text on a line
(`keys = [<<EOF`, `x = 1 /* old`) redacts every line to its close, however heredocs,
interpolations, and comments nest. A quoted string that ends at a line break, or
nesting deeper than 32 levels, is a lexing failure: every later line is redacted
whole. A detector
match blocks the allowlist even without a finding kind, so a token inside a
reference is not kept. A stored line is never a finding its raw line is not: a key-named
variable whose value is under the detector's six-character floor
(`api_token = "abc"`) becomes the whole-line `REDACTED_value`, because
`api_token = REDACTED_value` would match the detector.

Three Terraform evidence shapes are kept so relationship discovery still reads
them (the #8833 differential measured the loss without them):

- an `app_repo` or `app_name` value that is a name, `owner/name`, or a plain
  `https://host/path` URL with no userinfo, query, or fragment;
- a github.com URL, stored as `"https://github.com/<owner>/<repo>[/path]"` with
  its userinfo, query, and fragment dropped, as a value, a list element, or the
  only thing a comment keeps (`# https://github.com/...`); other comment text
  and other trailing text go;
- a GitHub Actions OIDC subject, `"repo:<owner>/<name>:<claim>"`.

A detector match on the line, with or without a finding kind, comes before
every evidence shape.

The stored body is not parseable HCL or JSON. Keys are kept when
they are names: an identifier, or a quoted key of letters, digits, `_`, `.`,
and `-` (`"us-east-1"`, `"app.example.com"`). A quoted key holding anything
else (a URL, a CIDR, an ARN, a password with symbols) takes the whole line. A
credential spelled as a plain name and used as a key survives unless the
detector flags it.

### What a governed row holds

For a `metadata` path, or a `redact` path whose redactor failed:

- `content` and `content_lower` are empty and `line_count` is `0`.
- `content_hash` is the digest of the **source file**, not of the stored body.
  Eshu computes it before the policy applies, so an unchanged file keeps the
  same freshness hint under every policy, and a policy change is detected by
  the registry fingerprint, not by the digest.
- No `content_file_secret_lines` or `content_file_references` row exists for the
  path, because both are derived from the stored body.
- `content_entities.source_cache` is empty. Under `redact` it is sliced from the
  redacted body, never from the source.
- The `content` fact carries an empty or redacted `content_body` and the source
  `content_digest`.
- Every emitter that reads the body gets the stored body, not the source: the
  service-catalog, workflow-image, documentation, CODEOWNERS, and `.gitmodules`
  facts. A definition that names `CODEOWNERS` or `.gitmodules` governs those
  files too, although they are read before the parser runs.

The parser still reads the original file. Its structured facts (the file fact
and the entities it extracts) are intended output and are not redacted, apart
from the whole-file `parsed_file_data.source` copy and the entity source
snippets, which carry the stored body. A parser can echo extracted values: the
`hcl` parser puts `.tf` resource attributes, variable defaults, and locals into
`parsed_file_data` and the entity metadata even under `metadata` (a test pins
it). A definition may bind `metadata` or `redact` only after that is proven: a
seeded full-stream scan over every path shape the definition covers
(`assertNoSeedInAnyFact`) must find no credential in any fact kind.

### Failure behavior

If the redactor returns an error, the file is not valid UTF-8, the body holds a
NUL byte (a BOM-less UTF-16 file does), or a `redact` body is over 4 MiB, Eshu
stores the `metadata` row for that path and counts it as
`eshu_dp_collector_content_store_files_total{outcome="redactor_failed"}`, with
`redactor` naming the mode that failed (`marker` or `skeleton`). It
never falls back to the raw body. The WARN log names the repo-relative path and
a bounded reason class, never the error text.

### Changing a policy

`Registry.Fingerprint` includes each definition's policy. A policy change moves
the fingerprint, so every repository re-collects once. The collector still emits
the content record for the path, with the new body and the source digest, so the
next generation overwrites the old row on a full snapshot and on a delta alike.
Rows in repositories that are not collected again keep their old bodies until
they are. A registry that binds no non-store policy keeps today's fingerprint.

### Which files use each policy

Four definitions bind a policy other than `store`, recorded in the
[credential-file design record](https://github.com/eshu-hq/eshu/blob/main/docs/internal/design/8813-credential-file-exposure.md).
Each credential file has its own parser definition, so the policy never reaches
other `.tf`, `.hcl`, `.yaml`, `.yml`, or `.ini` files. Every other definition
uses `store`.

| File | Definition | Policy | Mode |
| --- | --- | --- | --- |
| `.yarnrc.yml` | `yarnrc` (yaml engine) | `redact` | `marker`: credential keys `npmAuthToken` and `npmAuthIdent` at any nesting (top level, `npmScopes.*`, `npmRegistries.*`), URL userinfo keys `npmRegistryServer`, `npmPublishRegistry`, `httpProxy`, `httpsProxy` (#8833) |
| `*.tfvars`, `*.tfvars.json` | `tfvars` (hcl engine) | `redact` | `skeleton` (#8833) |
| `.npmrc` | `npmrc` | `metadata` | none (#8978) |
| `gradle-wrapper.properties` | `gradle_wrapper` | `metadata` | none (#8822) |
| `gradle.properties`, `nuget.config` | none | `metadata`, if a later record admits them | none |

The hcl engine parses a `.tfvars.json` body via `ParseJSON` since #9048,
projecting it onto the same body shape as the equivalent `.tfvars` file (line
numbers stay 0 by design); the skeleton policy applies as it does for `.tfvars`.

`.eshuignore` stays the per-repository override and drops the file's parser
facts as well.

## Build and tool configuration files

The `raw_text` row also admits small build and tool configuration files by exact
name, as searchable text only: `Makefile`, `GNUmakefile`, `justfile`,
`.editorconfig`, `.gitattributes`, `.dockerignore`, `.gitignore`, `.eslintrc`,
`.prettierrc`, `.babelrc`, `.npmignore`, `tox.ini`, `mypy.ini`, `pytest.ini`,
`.flake8`, `rustfmt.toml`, `clippy.toml`, `renovate.json5`, and
`.mvn/extensions.xml`. Admission is by name, never by extension, so other
`.ini`, `.toml`, `.xml` and `.properties` files stay unadmitted. A name that
matches in any directory is admitted at any depth.

Some names are left out on purpose:

- `Taskfile.yml` and `Taskfile.yaml` are already admitted as structured YAML
  through the `.yml` and `.yaml` extensions, so they are not re-listed.
- `.env`, `.pypirc`, `.netrc` and `settings.xml` hold credentials or
  environment values. `phpunit.xml`, `phpunit.xml.dist`, `.mvn/jvm.config` and
  `.mvn/maven.config` can hold environment values or `-D` credential properties
  too. The content store does not redact text on write, so none of them is
  admitted. `.npmrc` is the exception: it is admitted under `metadata`, so the
  repository tree and file counts keep the path, no body is stored, and its
  `registry=` and `@scope:registry=` URLs are reported with any userinfo, query,
  and fragment removed.
  `gradle-wrapper.properties` is the other exception (#8822): it is admitted
  under `metadata` because its `distributionUrl` can carry `user:password@`
  userinfo, and only the Gradle version and the `bin` or `all` distribution
  type are reported.

In filesystem source mode, the managed-workspace copy keeps the dot-prefixed
names the registry admits under the store policy, including the
runtime-version pins such as `.nvmrc` and `.tool-versions` (matched
case-insensitively) under non-hidden directories and under `.github`,
`.github/workflows` and `.mvn` — a new registry dotfile name needs no second
edit. Two exemptions stay out: `.gitignore`, which the copy must not duplicate
because it already applies the source repository's ignore rules, so `.gitignore`
is not indexed in that mode; and the names a metadata or redact policy governs
(`.npmrc`, `.yarnrc.yml`, `*.tfvars`), which stay pruned in filesystem mode even though
clone mode indexes them, as does any future dotfile a metadata or redact policy governs. Discovery then applies the registry to what the copy kept,
as it does in clone mode: `.mvn/extensions.xml` is admitted as text, a `.java`
file under `.mvn/wrapper` is admitted as Java, and `.mvn/jvm.config`,
`.mvn/maven.config` and `.mvn/wrapper/maven-wrapper.properties` have no registry entry, so they
are not indexed. The copy still prunes any other, unadmitted dot-directory
(other than a dot-directory whose name the registry itself admits)
whole, so an admitted name inside one, such as `tools/.config/.eslintrc`, is
indexed in clone mode only.
